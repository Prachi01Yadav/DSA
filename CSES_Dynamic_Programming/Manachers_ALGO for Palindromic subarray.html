1 The Mystery

Okay so here's the case, detective. You get an array of numbers, like:

nums = [1, -3, 2, 3, 2, -3, 1]

A palindrome is just a fancy word for "reads the same forwards and backwards." Like the word "mom" or "racecar." Same idea here but with numbers instead of letters.

A subarray just means a chunk of the array that's all next to each other (you can't skip around, no cherry-picking).

Your job: look at every possible chunk of the array, keep only the chunks that are palindromes (mirror-images of themselves), and out of those, find the one with the biggest sum.

Example walkthrough: In [1, -3, 2, 3, 2, -3, 1], the chunk [2, 3, 2] is a palindrome (reads the same both ways) and sums to 7. The whole array is ALSO a palindrome, but it only sums to 3. So 7 is the winner.

Why is this "Hard"? Because there could be a huge pile of possible chunks, and checking every single one the dumb way (character by character, chunk by chunk) is way too slow. That's where our detective tools come in.

2 Trick 1: Ripples in a Pond

Think about throwing a stone in a pond. Ripples spread out evenly from the center, in both directions at once. Palindromes work the exact same way — they have a center point, and they grow outward symmetrically.

So instead of checking random chunks, we pick a center, and grow outward one step at a time, checking "does the left side still match the right side?" The moment it stops matching, we stop — everything before that was a valid palindrome.

There are two kinds of centers: a single number can be a center (like the middle of "racecar" — length is odd), or the gap between two numbers can be a center (like the middle of "abba" — length is even). So we check both types of centers for every position.

This is simple, it's honest, and it works. It's just a little slow if we do it in the most basic way — but it's the foundation everything else builds on. Keep this ripple idea in your head, it's going to matter a lot in the next section.

3 Trick 2: Manacher's Algorithm — The Twin Trick

Manacher's algorithm is basically the "ripples in a pond" idea but with a genius shortcut: palindromes have twins.

The big "aha": Say you already found a huge palindrome stretching from position 10 to position 40, centered at position 25. Now you want to know the palindrome size at position 27. Well, position 27 has a "mirror twin" on the other side of the center — position 23. And you already know the answer for position 23! So instead of starting from zero and rechecking everything, you just copy that answer (with a small safety check) and save a ton of work.

That's it. That's the whole trick. Instead of blindly re-doing the ripple check every single time, Manacher's algorithm remembers the biggest palindrome found so far and its boundaries, and reuses mirror-twin information whenever possible. This takes it from slow to O(n) — it visits the whole array basically once.

The two little arrays it builds

Manacher's algorithm usually builds two arrays:

  • d1[i] — how far you can stretch out from position i as a center for odd-length palindromes (like "racecar").
  • d2[i] — how far you can stretch for even-length palindromes centered in the gap right before position i (like "abba").
Show me the Python code for Manacher's Algorithm 
# d1[i] = radius of the biggest ODD-length palindrome centered at i
# (radius 1 means just the single element itself)
def manacher_odd(arr):
    n = len(arr)
    d1 = [0] * n
    left, right = 0, -1   # the rightmost palindrome window found so far
    for i in range(n):
        # Use the mirror twin's answer as a starting guess (if inside the window)
        k = 1 if i > right else min(d1[left + right - i], right - i + 1)
        # Try to grow further, the honest "ripple" way
        while i - k >= 0 and i + k < n and arr[i - k] == arr[i + k]:
            k += 1
        d1[i] = k
        k -= 1
        if i + k > right:          # this palindrome reaches further right, update window
            left, right = i - k, i + k
    return d1

# d2[i] = radius of the biggest EVEN-length palindrome centered
# right between i-1 and i
def manacher_even(arr):
    n = len(arr)
    d2 = [0] * n
    left, right = 0, -1
    for i in range(n):
        k = 0 if i > right else min(d2[left + right - i + 1], right - i + 1)
        while i - k - 1 >= 0 and i + k < n and arr[i - k - 1] == arr[i + k]:
            k += 1
        d2[i] = k
        k -= 1
        if i + k > right:
            left, right = i - k - 1, i + k
    return d2
Honest note for THIS problem: Manacher's algorithm is amazing for finding the longest palindrome fast. But our problem wants the biggest sum, not the longest length — and because of negative numbers, sometimes a smaller palindrome has a bigger sum than the full-length one! So Manacher gets us the maximum stretch super fast, but we still need to peek at the smaller palindromes inside it too. It's a great skill to know (tons of other problems need exactly the longest-palindrome trick), just not the full silver bullet here on its own.

4 Trick 3: Hashing — The Fingerprint Trick

Imagine every chunk of the array gets its own unique "fingerprint" number. If two chunks have the same fingerprint, they're (almost certainly) the same sequence of numbers. This is called hashing, and the "hash-code equals" technique just means: instead of comparing chunks element-by-element (slow), you compare their fingerprints (instant).

How do we fingerprint a chunk instantly?

We treat the array like a number written in some weird base (like how "123" in base 10 means 1×100 + 2×10 + 3×1). We precompute a prefix hash array once, and then any chunk's fingerprint can be pulled out in O(1) using subtraction — just like prefix sums, but multiplication-flavored.

The palindrome check: Build a fingerprint array for the array forwards, and another one for the array reversed. To check if chunk nums[l..r] is a palindrome, just grab its forward fingerprint AND grab the fingerprint of that same stretch from the reversed array. If the two fingerprints match — boom, it's a palindrome. One quick comparison, no element-by-element checking needed!
Show me the Python code for rolling hash + palindrome check 
MOD = 1_000_000_007
BASE = 131

def build_hash(arr):
    n = len(arr)
    h = [0] * (n + 1)      # h[i] = fingerprint of arr[0..i-1]
    power = [1] * (n + 1)  # BASE^i, precomputed
    for i in range(n):
        h[i + 1] = (h[i] * BASE + arr[i]) % MOD
        power[i + 1] = (power[i] * BASE) % MOD
    return h, power

def range_hash(h, power, l, r):  # fingerprint of arr[l..r], inclusive
    return (h[r + 1] - h[l] * power[r - l + 1]) % MOD

def is_palindrome_subarray(nums, l, r, fwd, fwd_pow, rev, rev_pow):
    n = len(nums)
    forward_print = range_hash(fwd, fwd_pow, l, r)
    # the mirrored stretch inside the REVERSED array
    rl, rr = n - 1 - r, n - 1 - l
    backward_print = range_hash(rev, rev_pow, rl, rr)
    return forward_print == backward_print

# Usage:
# fwd, fwd_pow = build_hash(nums)
# rev, rev_pow = build_hash(nums[::-1])
# is_palindrome_subarray(nums, l, r, fwd, fwd_pow, rev, rev_pow)  -> True/False in O(1)!
Bonus power move: Because "is this a palindrome" is O(1) to check now, and because palindrome-ness is nested (if a big chunk centered at some point is a palindrome, every smaller chunk sharing that center is automatically a palindrome too), you can binary search for the largest palindrome radius at each center. That turns "find longest palindrome at every center" into O(n log n) instead of O(n²). Super handy trick to keep in your back pocket!

Real talk: in interviews/contests, people often use two different hash formulas (double hashing) to make fingerprint collisions basically impossible. Worth remembering if collisions ever bite you.

5 Cracking THIS Exact Problem

Now let's actually solve Palindromic Subarray Sum. Here's the plan, plain and simple:

  1. Build a prefix sum array so we can get the sum of any chunk in O(1) (add up front, subtract off, done).
  2. For every position, treat it as a center and do the "ripples in a pond" expand — for BOTH odd-length and even-length centers.
  3. Every time the ripple successfully grows (left number still equals right number), that whole chunk is a valid palindrome — check its sum and keep the biggest one you've seen.
Why not just take the biggest palindrome per center? Because of negative numbers! A smaller palindrome tucked inside a bigger one might have a bigger sum (the bigger one might include some negative junk dragging the total down). So we have to check every valid radius along the way, not just the maximum one. This is exactly why Manacher alone doesn't fully solve this — but the "expand and check every step" idea, powered by fast prefix sums, does the job perfectly. 
def maxPalindromeSum(nums):
    n = len(nums)
    prefix = [0] * (n + 1)
    for i in range(n):
        prefix[i + 1] = prefix[i] + nums[i]

    def range_sum(l, r):          # sum of nums[l..r], inclusive
        return prefix[r + 1] - prefix[l]

    best = max(nums)              # a single number is always a valid palindrome

    # odd-length palindromes: center is a single number
    for c in range(n):
        l, r = c, c
        while l >= 0 and r < n and nums[l] == nums[r]:
            best = max(best, range_sum(l, r))
            l -= 1
            r += 1

    # even-length palindromes: center is a gap between two numbers
    for c in range(n - 1):
        l, r = c, c + 1
        while l >= 0 and r < n and nums[l] == nums[r]:
            best = max(best, range_sum(l, r))
            l -= 1
            r += 1

    return best

# Quick check:
print(maxPalindromeSum([1, -3, 2, 3, 2, -3, 1]))  # -> 7
Time: O(n²) worst case (like when every number is the same — think [5,5,5,5,5], every center ripples all the way out).
Space: O(n) for the prefix sum array.

This is genuinely the expected solution for this problem — clean, easy to explain in an interview, and fast enough. The Manacher and hashing tricks you just learned are extra superpowers that make the closely-related "longest palindrome" family of problems blazing fast — you'll use them constantly in the practice problems below.

8 Cheat Sheet Recap

🪞 Palindrome = reads the same forward and backward.
🌊 Expand from center = grow outward from a point (or gap) while both sides keep matching.
👯 Manacher's Algorithm = expand from center, but reuse "mirror twin" answers so you never redo work. Gets you the longest palindrome everywhere in O(n).
🖐️ Hashing / fingerprint trick = give every chunk an instant fingerprint number so comparing chunks is O(1) instead of O(chunk length). Combine with binary search for O(n log n) longest-palindrome-per-center.
🎯 This problem's real solution = expand from center (both odd & even) + prefix sums, checking every radius along the way because negative numbers can make a smaller palindrome the winner.
