Can every city reach every other city?

A directed graph, a yes/no question, and a trick so efficient it feels like cheating: you never compare two cities to each other directly — you only ever look at one city, twice.

The problem, restated as a boarding pass

// input n cities, m one-way flights (a → b) // output YES if every city reaches every other city NO a b any pair where a cannot reach b
Where most people start

The honest-but-slow idea

"All cities reach all cities" sounds like it's about pairs of cities. So the obvious plan is: for every city, run a search (BFS/DFS) and see if it reaches everyone else. If every city passes, print YES.

Why it's too slow

Each search costs O(n + m). Doing one per city costs O(n · (n + m)). With n up to 100,000 and m up to 200,000, that's on the order of 10¹⁰ operations — far past what runs in a couple of seconds.

Why it's the wrong shape

You'd be proving n² individual facts ("A reaches B", "A reaches C", …) when the question only needs one global fact: is this whole graph one tightly-knit group?

The reframe

You don't need n cities. You need one.

Key insight

Pick any one city — say City 1 — and ask two questions instead of a million:
1) Can City 1 reach every other city?
2) Can every other city reach back to City 1?

If both answers are "yes," the whole network is fully connected — guaranteed, with zero further checking. That's the entire algorithm: two searches, from one node, instead of n searches from n nodes. This turns an O(n·(n+m)) problem into an O(n+m) one.

The proof

Why checking one city is enough to prove it for all of them

This isn't a heuristic or an approximation — it's an exact, airtight equivalence. Here's the chain of logic, one link at a time.

01

Pick any city, call it the hub.

It doesn't have to be City 1 — any city works, because strong connectivity is a property of the whole graph, not of any single city.

02

Suppose the hub can reach everyone, and everyone can reach the hub.

Take any two cities A and B, chosen completely at random. We want to know: can A reach B?

03

Route A through the hub.

A can reach the hub (given). The hub can reach B (given). Glue those two flight paths together — A → hub → B — and you have a valid route from A to B, even if no direct flight exists.

04

A and B were arbitrary.

Since this argument works for any pair you could name, every city can reach every other city. The graph is strongly connected — full stop.

05

The converse is trivial.

If the graph really is strongly connected, then in particular the hub can reach everyone and everyone can reach the hub — that's just a special case of "everyone reaches everyone."

06

So the two statements are equivalent.

"The whole graph is strongly connected" and "one chosen city has full outbound and inbound reachability" mean exactly the same thing. You only need to verify the second one, and it only takes two graph traversals.

The "inbound" trick: reverse the graph

Checking "can everyone reach the hub" directly would mean running a search backwards from every city — expensive again. Instead, flip every edge (a→b becomes b→a) and run one forward search from the hub on this reversed graph. Reaching a city in the reversed graph means that city could originally reach the hub. One flip turns an "everyone-to-one" question into a cheap "one-to-everyone" search.

The proof of "NO" is free

The problem doesn't just want YES/NO — it wants a witness pair when the answer is NO. You get this for nothing: whichever city the search never reaches is the counter-example. If the outbound sweep misses city X, print "hub X". If the inbound sweep misses city X, print "X hub". No extra computation required.

Putting it together

The algorithm, in four lines

  1. Build the flight graph, and a second copy with every flight reversed.
  2. BFS from city 1 on the original graph. If any city is unvisited, print NO and 1 <missing city>.
  3. BFS from city 1 on the reversed graph. If any city is unvisited, print NO and <missing city> 1.
  4. Otherwise, print YES.

Why this is fast enough

Naive: search from every city — O(n · (n + m))~10¹⁰ ops at n = 10⁵
Hub trick: search from one city, twice — O(n + m)~3×10⁵ ops

Both traversals together still only touch each city and each flight a constant number of times — so the total work barely grows even as the network gets huge.

Implementation

Clean, iterative BFS — no recursion, no surprises

BFS (not recursive DFS) avoids stack-overflow risk on long chains of cities, which matters once n reaches 100,000.

// CSES 1682 - Flight Routes Check
#include <bits/stdc++.h>
using namespace std;

int n, m;
vector<int> adj[100001], radj[100001];
bool vis[100001];

void bfs(vector<int> graph[], int start) {
    fill(vis + 1, vis + n + 1, false);
    queue<int> q;
    q.push(start);
    vis[start] = true;
    while (!q.empty()) {
        int u = q.front(); q.pop();
        for (int v : graph[u])
            if (!vis[v]) { vis[v] = true; q.push(v); }
    }
}

int main() {
    cin >> n >> m;
    for (int i = 0; i < m; i++) {
        int a, b; cin >> a >> b;
        adj[a].push_back(b);
        radj[b].push_back(a);   // build the reversed graph while reading input
    }

    bfs(adj, 1);                 // phase 1: outbound
    for (int i = 1; i <= n; i++)
        if (!vis[i]) { cout << "NO\n" << 1 << " " << i << "\n"; return 0; }

    bfs(radj, 1);                // phase 2: inbound
    for (int i = 1; i <= n; i++)
        if (!vis[i]) { cout << "NO\n" << i << " " << 1 << "\n"; return 0; }

    cout << "YES\n";
}
# CSES 1682 - Flight Routes Check
import sys
from collections import deque

def main():
    data = sys.stdin.buffer.read().split()
    idx = 0
    n = int(data[idx]); idx += 1
    m = int(data[idx]); idx += 1

    adj  = [[] for _ in range(n + 1)]
    radj = [[] for _ in range(n + 1)]
    for _ in range(m):
        a = int(data[idx]); idx += 1
        b = int(data[idx]); idx += 1
        adj[a].append(b)
        radj[b].append(a)          # reversed graph, built for free

    def bfs(graph, start):
        vis = [False] * (n + 1)
        vis[start] = True
        q = deque([start])
        while q:
            u = q.popleft()
            for v in graph[u]:
                if not vis[v]:
                    vis[v] = True
                    q.append(v)
        return vis

    vis1 = bfs(adj, 1)              # phase 1: outbound
    for i in range(1, n + 1):
        if not vis1[i]:
            print("NO"); print(1, i); return

    vis2 = bfs(radj, 1)             # phase 2: inbound
    for i in range(1, n + 1):
        if not vis2[i]:
            print("NO"); print(i, 1); return

    print("YES")

main()

Both solutions run in O(n + m) time and space — comfortably inside CSES's limits (n ≤ 10⁵, m ≤ 2×10⁵). Self-loops and duplicate flights don't break anything; a single-city network (n = 1) is trivially "YES".

Things that make this click

Facts worth remembering

01

Real airlines do this on purpose

Hub-and-spoke networks (Atlanta for Delta, Dubai for Emirates) exist for exactly this reason: routing every city through a small number of hubs guarantees connectivity with far fewer routes than connecting every city to every other one directly.

02

Undirected graphs don't need this trick

In an undirected graph, one flight both ways is automatic — one BFS from any node is enough to prove full connectivity. Directed graphs "pay a 2× tax" precisely because direction matters, which is why we need outbound and inbound checks.

03

The hub choice is arbitrary

You could run this exact check starting from city 7, or city 4,213 — any city gives the correct answer, because the property being tested belongs to the whole graph, not to whichever node you happened to pick.

04

It's half of a famous algorithm

This is essentially one round of Kosaraju's algorithm (S. Rao Kosaraju, 1978) for finding all strongly connected components in a graph — this problem just needs to confirm there's exactly one component covering everyone.

05

Reversing costs nothing extra

You don't need a separate pass to build the reversed graph — while reading each flight (a, b), push it into the forward list and push (b, a) into the reverse list in the same line of code.

06

Recursion can betray you here

A recursive DFS can blow the call stack on a graph shaped like one long chain of 100,000 cities. BFS with an explicit queue (as used above) never has this problem.

Where this pattern goes next

From "is it one group?" to "what are all the groups?"

This problem asks a yes/no question about the entire graph. The natural next step is: what if the graph isn't one strongly connected group — can you find the actual sub-groups (strongly connected components) where mutual reachability holds? That's Kosaraju's or Tarjan's algorithm, and it reuses the same reversed-graph idea, just applied more carefully across every unvisited node instead of just one hub.
