THE MECHANISM, PART 2

Shrinking kingdoms into dots: the condensation graph

Once you've found the kingdoms (SCCs), there's one more picture worth drawing — squash every kingdom down to a single dot. What's left is always simple, always clean, and it's the key to a whole family of harder problems.

Start here

What "condensing" even means

Take your galaxy. Every planet that belongs to the same kingdom — meaning every planet in that group can reach every other planet in that same group — gets squashed into one single dot.

That's it. That's the whole operation. You're not deleting information about which planets are in which kingdom — you're just zooming the camera out so far that an entire kingdom looks like one point, the same way a whole city looks like one dot on a map of the country.

Plain english

Condensation graph = "what does the map look like if I stop caring about individual planets, and only care about which kingdom connects to which kingdom?"

The squash

Now squash each kingdom into one dot

Forget the individual planets for a second. Ask only: does any teleporter leave Kingdom A and land somewhere in Kingdom B? Look at our 6 teleporters one at a time:

Why this matters

The squashed picture is always boringly simple

Here's the one fact that makes this whole idea worth learning: the condensation graph never has a cycle. It's always a DAG (a graph where arrows only ever point "forward", never loop back).

Why no cycles are possible

If Kingdom A → Kingdom B → Kingdom A were somehow possible, then any planet in A could reach any planet in B, and any planet in B could reach back to any planet in A — which by definition means A and B were never two separate kingdoms in the first place. They'd have already been merged into one. So by the time you're looking at the condensation graph, guaranteed, no cycles remain.

This is exactly the "shrink the kingdoms, get a clean DAG" idea from before — except now you're seeing it drawn out, not just described.

How to actually build it in code

Three simple steps

1

Label every planet with its kingdom number

Run Kosaraju's (or Tarjan's) exactly like before. Every planet gets a comp[planet] value — which kingdom it belongs to. You already have this from the SCC code.

2

Walk every original teleporter, once each

For each teleporter u → v, check comp[u] and comp[v]. If they're different kingdoms, that's a cross-kingdom edge — add an edge comp[u] → comp[v] in your new, smaller graph. If they're the same kingdom, skip it — it's an internal teleporter, it doesn't matter for the condensation graph.

3

(Optional) remove duplicate edges

If two different planets in Kingdom A both point into Kingdom B, you'll try to add the edge A → B twice. Depending on the problem, you may want to only keep it once — use a Set or check for duplicates before adding.

Minimal code sketch
List<List<Integer>> condensed = new ArrayList<>();
for (int i = 0; i <= kingdomCount; i++) condensed.add(new ArrayList<>());

for (int i = 0; i < m; i++) {
    int cu = comp[edgeU[i]];
    int cv = comp[edgeV[i]];
    if (cu != cv) {
        condensed.get(cu).add(cv);
    }
}
What it's used for

Why bother squashing at all?

Because a huge number of hard graph problems become easy once you realize: "the messy cyclic part only happens inside a kingdom — the part between kingdoms is always a clean DAG." Once you have a DAG, you unlock tools that don't work on graphs with cycles:

Topological order

DAGs can always be laid out left-to-right so every arrow points forward. This is exactly what let us decide "which kingdom needs a new road built into it" in the Reachability problem — a kingdom with zero incoming arrows in the condensation graph can never be reached without adding one.

DP on a DAG

Once cycles are gone, you can safely run dynamic programming over the condensation graph — process kingdoms in topological order, and by the time you reach one, every kingdom that feeds into it is already finished.

The pattern to remember

Any time a problem gives you a directed graph with cycles and asks something that "should" need a DAG (shortest path counts, reachability, longest chain, minimum edges to add) — the first move is almost always: find the SCCs, condense, then solve the easy DAG version.
