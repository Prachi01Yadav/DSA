Interval Scheduling — Pattern Map

Five recurring shapes behind almost every interval problem, and the one question that tells you whether to sort by start time or end time.

Quick lookup by what the problem asks for

Maximum number of non-overlapping intervals you can keep / fewest to removeSort by END, greedy pick
Max people/tasks alive at the same instant (just a count)Sweep line, +1/−1
Minimum meeting rooms / platforms needed (just a count)Sweep line, +1/−1
Which room each meeting goes into (actual allocation)Sort by START, min-heap of end times
Merge all overlapping intervals into blocksSort by START, merge in place
Attend one meeting/event per day, deadline-bound, tasks have a durationSort by deadline/END, max-heap for exchange argument
Free time common to everyone / gaps between busy blocksSweep line or merge, then read gaps
Pattern 1

Non-overlapping intervals (Activity Selection)

SORT BY END TIME

You're given start/end pairs and asked for the maximum count of intervals that don't overlap each other — or equivalently, the minimum number to delete so nothing overlaps.

Keywords that point here: "maximum non-overlapping intervals," "minimum intervals to remove," "erase overlap intervals," "maximum activities," "job sequencing without deadline pressure."
Arrays.sort(intervals, (a, b) -> a[1] - b[1]);   // sort by END
int count = 1;
int prevEnd = intervals[0][1];
for (int i = 1; i < intervals.length; i++) {
    if (intervals[i][0] >= prevEnd) {   // starts after (or when) prev ends
        count++;
        prevEnd = intervals[i][1];
    }
}
Why end time, not start: the interval that finishes earliest leaves the most room for everything that comes after it, regardless of when it started. Sorting by start and greedily taking the first one can lock in a long interval that blocks out several short ones later. This is the classic exchange-argument greedy proof.
Pattern 2

Sweep line (+1 / −1)

EVENTS SORTED BY TIME

You only need a number — the max overlap at any instant, or the minimum resources (rooms, platforms, servers) needed at peak load. You don't care which interval got which resource.

Keywords that point here: "minimum platforms," "minimum meeting rooms required" (count only), "maximum overlapping intervals," "peak concurrent users," "car pooling capacity check."
List events = new ArrayList<>();
for (int[] iv : intervals) {
    events.add(new int[]{iv[0], 1});    // arrival
    events.add(new int[]{iv[1], -1});   // departure
}
events.sort((a, b) -> a[0] != b[0] ? a[0] - b[0] : a[1] - b[1]); // end before start on ties, if intervals are half-open

int cur = 0, peak = 0;
for (int[] e : events) {
    cur += e[1];
    peak = Math.max(peak, cur);
}
Why this is different from Pattern 1: here you're not selecting a subset of intervals — every interval is "active," you're just measuring how many overlap at once. There's no greedy choice being made, so there's no start-vs-end dilemma; you sort events, not intervals, and the tie-break (process an ending before a starting event at the same timestamp) matters only if the interval is closed at both ends.
Pattern 3

Room allocation (Meeting Rooms II)

SORT BY START TIME

Same flavor as Pattern 2, but now you need the actual assignment — which room each meeting uses — not just the peak count. This is where a min-heap enters.

Keywords that point here: "minimum rooms and assign each meeting a room," "schedule tasks on k machines," "how the rooms were allocated," "reuse the earliest-freed resource."
Arrays.sort(intervals, (a, b) -> a[0] - b[0]);   // sort by START
PriorityQueue endTimes = new PriorityQueue<>();  // min-heap of end times
for (int[] iv : intervals) {
    if (!endTimes.isEmpty() && endTimes.peek() <= iv[0]) {
        endTimes.poll();     // earliest-freed room is free — reuse it
    }
    endTimes.offer(iv[1]);   // occupy a room until this end time
}
int roomsNeeded = endTimes.size();
Why start time here, when Pattern 1 used end time: you're processing meetings in the order they arrive, and for each new arrival asking "is any room about to be free?" That question only makes sense if you walk through arrivals chronologically. The heap tracks the earliest end time among busy rooms, so it plays the role end-time-sorting played in Pattern 1 — but here it's dynamic (updated per arrival) instead of a static sort key, because you must decide room-by-room, not just count.
Pattern 4

Merge intervals

SORT BY START TIME

Collapse overlapping or touching intervals into their union. Foundation for "insert interval," "employee free time," and "list of busy blocks."

Keywords that point here: "merge overlapping intervals," "combine intervals," "consolidate ranges," "insert interval into sorted list."
Arrays.sort(intervals, (a, b) -> a[0] - b[0]);  // sort by START
List merged = new ArrayList<>();
for (int[] iv : intervals) {
    if (merged.isEmpty() || merged.get(merged.size()-1)[1] < iv[0]) {
        merged.add(iv);
    } else {
        merged.get(merged.size()-1)[1] =
            Math.max(merged.get(merged.size()-1)[1], iv[1]);
    }
}
Why start time: you're building up a union left to right, so you need intervals in the order they begin — you're not choosing a subset (no greedy trade-off), just accumulating coverage, so there's no reason to prefer end time here.
Pattern 5

Deadline-bound task scheduling (Job Sequencing / "Course Schedule III")

SORT BY DEADLINE (END)

Each task has a duration and a deadline; you attend/complete as many whole tasks as possible without missing any deadline — but unlike Pattern 1, tasks aren't fixed [start, end] windows, so you sometimes need to evict an already-accepted task later if a better one shows up.

Keywords that point here: "maximum number of courses you can take before deadlines," "job sequencing to maximize profit," "task scheduler with deadlines," "you may drop an earlier choice if it helps."
Arrays.sort(tasks, (a, b) -> a[1] - b[1]);  // sort by deadline
PriorityQueue taken = new PriorityQueue<>(Collections.reverseOrder()); // max-heap of durations
long time = 0;
for (int[] t : tasks) {
    time += t[0];              // tentatively take it
    taken.offer(t[0]);
    if (time > t[1]) {         // blew the deadline
        time -= taken.poll();  // evict the LONGEST task taken so far
    }
}
int maxTasksAttended = taken.size();
Why this looks like Pattern 1 but needs a heap: sorting by end/deadline is still right, for the same exchange-argument reason as Pattern 1 — but because a task has a duration that eats into the schedule (not just an instantaneous slot), a task you accepted early can later become the thing worth undoing. The max-heap lets you cheaply find "the most expensive choice so far" to undo, which is what you were groping toward with "attend a tiny bit, not the whole interval" — you're not partially attending anything, you're conditionally un-committing to a full task.

The one-line rule for start vs. end

Sort by END
when you're picking a subset of intervals/tasks and want to leave maximum room for the future (Patterns 1 and 5). This is a greedy selection problem.
Sort by START
when you're processing arrivals in real time — building a union (Pattern 4) or assigning live resources as they show up (Pattern 3). This is a simulation problem.
Sweep line
when you don't care about individual intervals at all, only the count of overlaps at some moment (Pattern 2). Sort events, not intervals.
